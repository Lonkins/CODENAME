# ADR 0003: Frame pacing

- Status: Accepted
- Date: 2026-08-29

## Context

A libretro core wants to run at its system's native rate (`retro_get_system_av_info().timing.fps` — e.g. 60.0988 Hz NTSC SNES, 59.92 Hz Mega Drive). The display refreshes at its own rate (60 Hz, or 120 Hz ProMotion). Audio is generated by the same `retro_run` calls that produce video, so the two cannot be paced independently: pace video naively and audio under/overruns; pace audio naively and video judders. This is where most frontends go wrong, so the approach is fixed before the renderer is built.

Constraints from ADR 0001/0002: core on a dedicated thread; presentation via `CAMetalDisplayLink`; audio through a lock-free SPSC ring into `AVAudioEngine`; no allocation or locking on the audio render thread.

## Options

### 1. Audio-master

Core runs on its own timer, throttled by audio-ring occupancy; display samples the latest completed frame each vblank.

- ✅ Audio never glitches by construction.
- ❌ Video cadence is uncontrolled: frames beat against vblank, producing periodic judder — visibly wrong for scrolling 2D games, which is this project's bread and butter.

### 2. Free-run + triple buffering

Core free-runs at native rate on a high-resolution timer; renderer displays the newest complete frame.

- ❌ Same judder as option 1 plus an extra frame of latency and more buffer management. Decoupling maximal, correctness minimal.

### 3. Video-master with dynamic rate control — **chosen**

The display link is the clock. Each `CAMetalDisplayLink` callback drives exactly one `retro_run` on the core thread (via a semaphore — the display link thread never runs core code). Core rate and refresh rate differ by a small factor (60.0988/60 ≈ +0.16%), so the core is effectively run at display rate; the resulting audio drift is absorbed by **dynamic rate control**: the audio resample ratio is nudged continuously by ring-buffer occupancy (target 50% fill), clamped to a maximum deviation `d` (default 0.005), exactly the published libretro technique. Pitch shift at ≤0.5% is inaudible; buffer occupancy becomes self-regulating, so there is no accumulating drift, no dropped audio, and a fixed video cadence — one core frame per vblank, zero judder.

- 120 Hz displays: run one core frame every `round(refresh / coreFPS)` vblanks (2 at 120 Hz); same math, same rate control.
- Mismatch guard: if `|refresh / N − coreFPS| / coreFPS > 0.05` (e.g. PAL 50 Hz content on a fixed 60 Hz panel), pacing falls back to audio-master (option 1) for that session rather than pitch-bending audio by 20% — correctness over cadence when the hardware genuinely cannot match.
- Fast-forward/pause are trivial: run N core frames per vblank / run none.

## Latency policy

Single-frame pipeline: `retro_run` writes the framebuffer, the same vblank's render encodes and presents it. The `CAMetalDrawable` is acquired only after the frame is complete (late-latch). No frame queue. If the core misses its deadline (heavy frame), the previous texture is re-presented and the core continues — one repeated frame, no queue growth.

## Consequences

- The audio resampler must support a continuously variable ratio; ratio updates are computed on the core thread and read by the render callback via an atomic — no locks.
- The session layer owns a pacing state machine (video-master / audio-master fallback / fast-forward); it is pure logic and gets unit tests (given core fps + refresh sequences, assert run-cadence and ratio adjustments).
- A pacing harness (Phase 1 conformance tests) counts repeated/dropped frames and asserts bounded ring occupancy over simulated minutes.
- VRR/adaptive-sync displays are not specially handled in Phase 1; the mismatch guard covers them conservatively. Revisit if ProMotion VRR proves better served by driving the display link at core rate.

## Amendment (2026-08-31): the fallback, as built

The mismatch guard above was decided and then not implemented: both display
loops matched only on video-master, so `.audioMaster` left one core frame per
vblank in place and ran 50 Hz content at 60 — the exact failure the guard
existed to prevent, with dynamic rate control clamped far too tightly to
absorb it.

It ships now, and not as option 1's separate core-rate timer. Both modes are
expressed as one per-vblank quantity — frames due per vblank, accumulated
across vblanks — so video-master is `1/N` and the fallback is
`coreFPS / refresh`. Fractional rates come out exact in the long run (5 core
frames per 6 vblanks for PAL on 60 Hz), the core keeps running on its own
thread driven by the display link, and neither loop grows a second code path.
Catch-up is capped so a hitch cannot turn one vblank into an unbounded burst.

What this does not do: it does not remove the judder inherent to 50 on 60 —
frames still beat against vblank, which is why video-master is preferred
whenever a divisor fits. It buys correct rate and correct audio, which is
what the guard was for.
